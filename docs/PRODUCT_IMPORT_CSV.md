# Product Import CSV

**Endpoint:** `POST /api/v1/admin/products/import`  
**Authentication:** Sanctum admin access  
**Last verified:** October 9, 2026

Upload a CSV as `multipart/form-data` with:

- `file`: CSV/plain-text file, maximum 5 MB.
- `dry_run`: required boolean. String values such as `true`, `false`, `1`, and `0` are normalized before validation.

Always run with `dry_run=true` first. A preview performs the same row validation and create/update classification without writing data, and shows what each update row would change.

## File-level rules

- The file must be UTF-8 encoded. In Excel, save as **CSV UTF-8 (Comma delimited)**. Other encodings are rejected with `422` and the message `CSV must be UTF-8 encoded. In Excel use "CSV UTF-8 (Comma delimited)".`
- The delimiter is detected from the header line: comma (`,`), semicolon (`;`), or tab. The most frequent of the three outside quotes wins; comma is the default. Excel in many European locales exports `;`, which works without changes.
- The first non-blank row is the header. A UTF-8 BOM on the first header is accepted.
- Header names are case-insensitive and trimmed: `Type`, ` SKU `, and `sku` are the same column.
- Headers must be unique (after lower-casing) and non-empty.
- `type`, `sku`, and `name` headers are mandatory.
- At least one data row is required; the maximum is 5,000 data rows.
- Unknown columns are ignored and listed in `data.warnings` (for example `Unknown column "stok_qty" is ignored.`). Warnings never block an import.
- Blank lines, and rows that contain only delimiters (for example `,,,,` rows Excel leaves at the end of a sheet), are skipped.
- Empty cells are omitted from the row: an omitted value never changes the stored value on update.
- The literal `NULL` (any case) is converted to a real null value, which clears a nullable field on update. Columns that cannot be null in the catalog (`name`, `price`, `stock_qty`, `status`, `in_stock`, `is_featured`) reject `NULL` with a row error.
- `options` and `attributes` are JSON strings in the CSV. A value that is not valid JSON reports `<field> must be valid JSON.`; valid JSON that is not an array/object reports `The <field> field must be an array.`
- SKUs and `parent_sku` are trimmed and compared case-insensitively everywhere: duplicates within the file, matching existing products/variants, and matching a variant's `parent_sku` to a product row in the same file.

## Row numbers

Each result row reports `row`, the spreadsheet row number: the header is row 1, blank lines count as rows (exactly as a spreadsheet shows them), and a quoted cell that contains line breaks stays within one row.

## Product rows

Set `type` to `product` (case-insensitive).

| Column | Required | Rules and behavior |
|---|---:|---|
| `type` | Yes | Must be `product` |
| `sku` | Yes | String, max 255; creates or updates by SKU (case-insensitive); cannot collide with a variant or soft-deleted product |
| `name` | Yes | String, max 255 |
| `slug` | No | String, max 255; uniqueness is generated by the backend |
| `description` | No | String, max 10,000 |
| `price` | On create | Number, minimum 0. Required when the SKU is new; on update an omitted price keeps the stored price |
| `discount_price` | No | Number, minimum 0; must be strictly less than the final price (the row price, or the stored price when the row omits it) |
| `stock_qty` | No | Integer, minimum 0; if `in_stock` is omitted, it is derived from this value. See the variant stock rule below |
| `status` | No | `draft`, `published`, or `archived`; new products default to `draft`, existing products retain status when omitted |
| `category_slug` | For published products | Must identify an existing, non-deleted category. Omitted or empty keeps the current category; `NULL` clears it |
| `in_stock` | No | Boolean (`true/false`, `1/0`, and standard boolean spellings accepted by PHP normalization) |
| `is_featured` | No | Boolean |
| `meta_title` | No | String, max 255 |
| `meta_description` | No | String, max 1,000 |
| `options` | No | Valid JSON array/object |
| `weight_oz` | For published products | Number greater than 0, maximum 2,400 |
| `length_in` | For published products | Number greater than 0, maximum 200 |
| `width_in` | For published products | Number greater than 0, maximum 200 |
| `height_in` | For published products | Number greater than 0, maximum 200 |

### Publish rules use the final product state

Publish rules are checked against the product as it will be after the import: the stored values, overlaid with the values the row provides (including explicit `NULL`). A published product needs a category and all four of `weight_oz`, `length_in`, `width_in`, `height_in` greater than 0. Which fields are checked:

- **New product, or the row has a `status` value of `published`:** all publish fields are checked (same as the admin update endpoint when `status=published` is sent).
- **Existing published product, row without `status`:** only the publish fields the row itself sets are checked, so an import can't break a published product, and a published product with incomplete data can still receive unrelated updates (e.g. stock or price).

Consequences:

- A row containing only `type,sku,name,status=published` publishes an existing product that already has a category and complete dimensions.
- `weight_oz=NULL` (or `category_slug=NULL`) on a product that is or will be published is rejected.
- A published product that is missing a dimension can still have its `stock_qty` updated; sending `status=published` for it is rejected until the row supplies the missing values.

Messages match the admin product endpoints: `Published products require a category.` (key `category_slug`) and `Published products require complete shipping weight and dimensions.` (key per dimension).

## Variant rows

Set `type` to `variant` (case-insensitive). Products are committed before variants, so `parent_sku` may reference a product row in the same CSV.

| Column | Required | Rules and behavior |
|---|---:|---|
| `type` | Yes | Must be `variant` |
| `sku` | Yes | String, max 255; creates or updates a variant by SKU and cannot collide with any product SKU |
| `parent_sku` | Yes | Existing product SKU or product SKU in the same file (case-insensitive); must differ from variant SKU |
| `name` | Yes | String, max 255 |
| `price` | No | Number, minimum 0 |
| `stock_qty` | No | Integer, minimum 0 |
| `attributes` | No | Valid JSON array/object |
| `weight_oz` | No | Number greater than 0, maximum 2,400 |
| `length_in` | No | Number greater than 0, maximum 200 |
| `width_in` | No | Number greater than 0, maximum 200 |
| `height_in` | No | Number greater than 0, maximum 200 |

- **A variant cannot move between products.** If the variant SKU already exists under a different product than `parent_sku`, the row fails with `SKU belongs to a variant of another product (<current parent sku>).` This includes pointing an existing variant at a product that is being created in the same file.

### Variant stock rule

For every product touched by the file (a product row, or the parent of a variant row), the sum of its final variant stock must not exceed its final product stock — the same rule the admin product endpoints enforce.

- Final product stock: the row `stock_qty`, otherwise the stored value, otherwise 0 for a new product.
- Final variants: the product's stored variants, with any variant that appears in the file replaced by its row (row `stock_qty`, otherwise its stored stock, otherwise 0), plus new variants from the file.
- Only checked when the product ends up with at least one variant.

On violation, every variant row of that product in the file, and the product row if present, gets a `stock_qty` error: `The total stock quantity of variants (X) cannot exceed the product's stock quantity (Y).` Lowering a product's stock below its existing variants' total is rejected the same way.

## Type errors

A row whose `type` is not `product` or `variant` reports only `type: ["Type must be product or variant."]`; no other check runs for that row, and it counts as an error row.

## Example

```csv
type,sku,parent_sku,name,price,stock_qty,status,category_slug,in_stock,is_featured,attributes,weight_oz,length_in,width_in,height_in
product,QUEEN-BAG-001,,Queen Bag,129.00,20,published,bags,true,false,,24,14,10,5
variant,QUEEN-BAG-001-BLK,QUEEN-BAG-001,Queen Bag - Black,129.00,8,,,,,"{""color"":""Black""}",24,14,10,5
```

## Atomicity and response

- Any row error prevents all writes, even when `dry_run=false`.
- A valid `dry_run=false` import writes all product rows and then all variant rows inside one database transaction.
- Each result row reports:
  - `row`, `type`, `sku`, `action` (`create`, `update`, or `error`), and field-keyed `errors`;
  - `changes`: for `update` rows, an object `{ "field": [old, new] }` with only the fields whose value actually changes (decimals compared and shown with 2 decimals, booleans as booleans, JSON compared by value; `category_id` is shown as category ids; `slug` is not previewed because it is generated at commit time). An update that changes nothing returns `{}`. `create` and `error` rows return `null`.
- `data.warnings` lists ignored unknown columns (empty array when none).
- A successful commit (not a preview) is recorded in the admin audit log as `import_products`, with the summary and the first 100 SKUs.

Successful preview/import returns `200`:

```json
{
  "success": true,
  "message": "CSV preview completed.",
  "data": {
    "summary": {

```

## Status codes

| Status | Meaning |
|---|---|
| `200` | Preview completed, or import committed |
| `422` | File-level error (`errors.file`, `data: null`) or one or more row errors (`data` has the full analysis, `errors.rows` repeats the rows). Nothing was written |
| `409` | `The catalog changed during import; run the preview again.` Another write (for example a product created with the same SKU) happened between validation and commit. The whole import was rolled back; run the preview again and resubmit |
